Building Multi-Tenant Architecture for Notification SaaS

A notification SaaS must deliver the right message with the right branding to the right person every time. Get the tenant model wrong, and you leak data or send a customer's email with another company's logo. Get it right, and product teams ship faster without rebuilding routing logic for every new account.

Courier makes the case for tenant-aware notification infrastructure in their multi-tenant notifications post.

Prerequisites

  • Node.js 18+, a cloud account (AWS, Azure, or GCP), and a notification provider account (SendGrid, Twilio, or FCM)
  • Familiarity with REST APIs and JSON Schema Access to the AWS multi-tenant architectures guide

Choosing a Tenant Isolation Model

AWS defines three database-tier patterns that map directly to notification systems.

Silo model. Each tenant gets a dedicated application stack and database instance. Traffic and data never cross boundaries. This gives the strongest isolation and the highest cost. Use it when a single tenant's compliance requirements forbid shared infrastructure.

Bridge model. Tenants share the application stack and compute but each owns a dedicated schema (or database in PostgreSQL). RDS Proxy can multiplex connections only when tenants authenticate with the same database user; unique users per tenant fragment the pool into micro-pools. This model balances cost and isolation for most B2B SaaS.

Pool model. Tenants share the entire stack, database instance, and tables. Row-level security enforces isolation. Lowest cost, highest operational complexity. Choose this when you have thousands of small tenants and can invest in RLS policy testing.

Pick the model before you write schema migrations. Changing isolation later requires a full data migration.

Designing the Tenant Data Schema

A tenant record is the control plane for every notification sent on behalf of a customer account. Courier's tenant deep-dive shows a working version of this tenant object, with brand, preferences and parent tenant on one record. Courier's tenant object stores five fields that cover the common cases:

id. Your internal account identifier (e.g., acme-corp).

brand_id. Pointer to a brand asset (logo, colors, footer).

default_preferences. Starting opt-in/opt-out status per topic for every user in the tenant.

properties. Free-form metadata: plan, region, support email, account manager.

parenttenantid. Optional link to a parent for hierarchical inheritance.

Channels, email/SMS provider credentials, and API keys stay at the workspace/environment level. They are not tenant fields. A tenant can carry a customer's own Slack access_token or Microsoft Teams service_url inside user_profile so sends scoped to that tenant route through the customer's workspace instead of yours.

Implementing Per-Tenant Branding Resolution

When your app posts an event, the notification layer resolves the brand in a fixed priority chain:

  1. brand_id on the send request (explicit override)
  2. The tenant's brand_id (auto-inferred default)
  3. The template's assigned default brand
  4. The workspace primary brand

This means a single template renders with Acme's logo for Acme users and Beta's logo for Beta users without any conditional code in your application. Tenant templates (API-only) let a customer override one template's content while every other tenant keeps the default.

Managing Provider Credentials Per Tenant

Email and SMS providers (SendGrid, Twilio, SES, Sinch) are configured once per environment. Every tenant uses them. This keeps secret rotation simple and avoids per-tenant deliverability reputation fragmentation.

For chat channels the pattern differs. A tenant's user_profile can store a customer's Slack bot token or Microsoft Teams tenant_id and service_url. When you send with tenant_id: "acme-corp", the notification layer merges that profile into the recipient at send time, so the message posts to Acme's Slack workspace instead of yours. The same user ID in two tenants produces two different deliveries with two different chat backends.

Do not store customer Slack tokens in your application database. Keep them in the notification layer's tenant user_profile where they are scoped, encrypted, and rotated independently.

Enforcing Tenant-Scoped Preference Defaults

default_preferences is a complete list of topic statuses (e.g., OPTED_IN, OPTED_OUT, REQUIRED). When a child tenant sets any item, it replaces the parent's entire list; it does not merge topic by topic. To override one topic and keep the rest, copy the parent's full list into the child and change only that topic.

The precedence chain at send time is:

  1. User's explicit preference (stored on the user profile)
  2. Tenant default_preferences (merged down the parent chain, child over parent)
  3. Workspace default for the topic

Courier loads tenant context as a four-layer sliding window. In a five-level hierarchy, the top tenant's settings do not apply to a leaf send. Keep trees to four levels or replicate required settings at each level.

Routing Notifications Through Tenant Context

Your application code states what happened and names the tenant. The notification layer decides channel, timing, branding, and preferences in a single endpoint call.

// Your application
await courier.send({
 event: "report.ready",
 recipient: userId,
 tenant_id: "acme-corp",
 data: { reportUrl: "https://app.acme.com/reports/42" }
})

The notification layer then:

  1. Loads the tenant chain for acme-corp (brand, preferences, properties, user_profile)
  2. Merges the recipient's user profile
  3. Resolves the brand via the chain in Figure 1
  4. Evaluates preferences (user > tenant > workspace)
  5. Renders the template per channel with tenant properties available as {{tenant.properties.plan}}
  6. Routes to providers: shared email/SMS, tenant-scoped Slack/Teams from user_profile

One endpoint call replaces the lookup, rendering, and routing code you would otherwise maintain per channel.

Testing Tenant Isolation Locally

Spin up a sandbox environment with test vendors (SendGrid sandbox, Twilio test credentials, FCM debug tokens). Create two tenant records:

{ "id": "tenant-a", "brand_id": "brand-a", "default_preferences": [{ "topic": "billing", "status": "REQUIRED" }] }
{ "id": "tenant-b", "brand_id": "brand-b", "default_preferences": [{ "topic": "billing", "status": "OPTED_OUT" }] }

Send the same event to the same user ID scoped to each tenant. Verify:

  • Email header/logo matches the tenant's brand
  • Billing notification delivers for tenant-a, blocks for tenant-b
  • Slack message posts to tenant-a's workspace when user_profile.slack.access_token is set, falls back to your workspace when absent
  • Logs show the resolved tenant_id, brand_id, and preference decision per recipient

What you learned

  • Choose silo, bridge, or pool isolation before you model data; bridge fits most B2B notification SaaS.
  • Tenant records hold brand, default preferences, properties, and optional parent links; providers stay at workspace level.
  • Brand resolution follows a four-step chain; tenant templates allow per-customer content overrides.
  • Chat provider credentials live in user_profile per tenant; email/SMS providers are shared.
  • Preference defaults replace (not merge) down the hierarchy; keep trees to four levels.
  • One send call with tenant_id replaces per-channel routing code in your application.
  • Test isolation with a sandbox matrix: same user, different tenants, verify brand, preference, and provider routing.
