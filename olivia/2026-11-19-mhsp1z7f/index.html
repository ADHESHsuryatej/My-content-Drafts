Building multi-tenant notification architecture for a notification SaaS

A notification SaaS that serves multiple customers from one codebase must isolate branding, credentials, and preferences per tenant without custom code per account. Get it right, and a new customer onboards in minutes. Get it wrong, and you ship one tenant's logo in another's email or leak an API key across accounts. You also need to handle mobile push through APNs and FCM, web push via the Push API, and email deliverability with DMARC.

Prerequisites

  • Node 20+ runtime
  • PostgreSQL 15+ database
  • Provider accounts for email and SMS (for example, SendGrid, Twilio)

Designing the tenant and user schema

Create four tables: tenants, users, tenant_memberships, and tenant_branding. The tenants table holds the external ID you already use (acme-corp), a display name, and an optional parent tenant for hierarchies. tenant_memberships links users to tenants with a role column so the same person can belong to several workspaces. tenant_branding stores a JSONB column with logo URL, primary color, email header HTML, and footer HTML. Keep branding in JSONB so you can add fields without migrations.

create table tenants (
 id uuid primary key default gen_random_uuid(),
 external_id text unique not null,
 display_name text not null,
 parent_id uuid references tenants(id)
);

create table users (
 id uuid primary key default gen_random_uuid(),
 email text unique not null
);

create table tenant_memberships (
 tenant_id uuid references tenants(id),
 user_id uuid references users(id),
 role text not null default 'member',
 primary key (tenant_id, user_id)
);

create table tenant_branding (
 tenant_id uuid primary key references tenants(id),
 config jsonb not null default '{}'
);

Storing per-tenant provider credentials

Never put a SendGrid API key or Twilio Account SID in your application config. Encrypt each credential with a per-tenant envelope key stored in a vault (AWS KMS, HashiCorp Vault, or your cloud provider's secret manager) and persist only the ciphertext and key ID in a tenant_credentials table keyed by tenant_id and channel. At send time, the worker fetches the row, decrypts in memory, and passes the plaintext to the provider SDK. The plaintext never hits logs or the database.

create table tenant_credentials (
 tenant_id uuid references tenants(id),
 channel text not null, -- 'email' | 'sms'
 ciphertext bytea not null,
 key_id text not null,
 primary key (tenant_id, channel)
);

Resolving preference defaults per tenant

Preferences resolve in layers, each overriding the one above:

  1. Workspace default (your product's baseline)
  2. Parent tenant default (if you nest tenants)
  3. Tenant default (the customer's choice)
  4. User global preference
  5. User preference scoped to the tenant

Store each layer in its own table (workspace_prefs, tenant_prefs, user_prefs, user_tenant_prefs) with columns topic, channel, status (opted_in, opted_out, required). At send time, walk the layers in order and return the first explicit value. This layered model matches how Courier and Knock resolve preferences per tenant.

Scoping in-app inbox feeds to the active tenant

When a user opens your app, they hold an active tenant_id in session. The inbox query filters messages where message.tenant_id = active_tenant_id so a user who belongs to Acme and Globex sees only Acme notifications while in Acme's workspace. If you nest tenants, include descendant tenant IDs in the filter. The same rule applies to unread counts and push payloads: tag every message with its tenant at write time.

Routing a notification through the tenant context

Build a sendNotification({ tenantId, userId, topic, payload }) function that:

  1. Loads tenant_branding.config and merges it into the template context.
  2. Decrypts tenant_credentials for each channel the topic uses.
  3. Resolves the preference stack for userId + tenantId; abort if the resolved status is opted_out or opt_in_required.
  4. Renders the channel template (Handlebars or React Email) with branding variables.
  5. Calls the provider SDK with the decrypted credentials.
  6. Writes a log row keyed by tenant_id, user_id, message_id, provider response, and latency.

The function is pure apart from the provider call, so you can unit-test every branch with mocked decryption and preference resolution.

Testing isolation with two tenant fixtures

Seed two tenants: tenant_a (branding blue, SendGrid key A, billing alerts required) and tenant_b (branding green, SendGrid key B, product announcements opted out). Call sendNotification for a user who belongs to both, once with tenant_a and once with tenant_b. Assert that:

  • The email HTML contains the correct logo and color.
  • The SendGrid API request uses the matching API key.
  • The preference check blocks the product announcement for tenant_b but delivers the billing alert for tenant_a.

Run the fixtures in CI on every PR; they catch cross-tenant leaks before they reach production.

Wrapping up

  • Schema. Tenants, memberships, and JSONB branding keep identity and look-and-feel isolated.
  • Credentials. Per-tenant envelope encryption in a vault prevents key leakage.
  • Preferences. Five-layer resolution lets each customer set their own defaults while users keep personal overrides.
  • Inbox. Filtering by active tenant_id makes the feed feel native to the workspace.
  • Send function. A single code path that loads branding, decrypts credentials, resolves preferences, renders, and logs keeps the surface area small and testable.

Together these pieces make multi-tenant notifications feel like a first-class feature of every customer's product, not a shared service with leaks.
