How to set up multi-channel notifications

Multi-channel notifications let you reach users on email, push, SMS, and in-app from a single event. Get the routing right and users see the message where they expect it. Get it wrong and you send SMS at 3 a.m. to someone who only wanted email.

Prerequisites

  • AWS account with programmatic access
  • Verified domain in Amazon SES
  • Amazon SNS topics for FCM, APNs, and SMS
  • A user profile store (DynamoDB, Postgres, or your existing database) that holds channel opt-ins, quiet hours, and timezone per user

Setting up the project

Create a Node.js service and install the AWS SDK v3 modules you need.

mkdir notification-service && cd notification-service
npm init -y
npm i @aws-sdk/client-ses @aws-sdk/client-sns @aws-sdk/client-dynamodb

Configure credentials and region once, then reuse the clients.

// config/aws.js
import { SESClient } from "@aws-sdk/client-ses";
import { SNSClient } from "@aws-sdk/client-sns";
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
​
export const ses = new SESClient({ region: "us-east-1" });
export const sns = new SNSClient({ region: "us-east-1" });
export const db  = new DynamoDBClient({ region: "us-east-1" });

Building the notification routing logic

Your router receives an event type and a payload, looks up the user's preferences, then decides which channels fire. A switch statement works for a handful of events; plan to split it into separate handlers once you pass ten types.

// services/router.js
import { ses } from "../config/aws.js";
import { sns } from "../config/aws.js";
import { getPreferences } from "./preferences.js";
​
export async function routeNotification(userId, eventType, payload) {
  const prefs = await getPreferences(userId);
  if (!prefs.enabled) return;
​
  const channels = decideChannels(eventType, prefs);
  await Promise.all(
    channels.map((ch) => sendViaChannel(ch, userId, eventType, payload))
  );
}
​
function decideChannels(eventType, prefs) {
  switch (eventType) {
    case "order_confirmed":
      return prefs.email ? ["email"] : [];
    case "payment_failed":
      return prefs.sms ? ["sms"] : prefs.email ? ["email"] : [];
    case "new_message":
      return prefs.push ? ["push"] : prefs.email ? ["email"] : [];
    default:
      return [];
  }
}

Adding user preferences and profile storage

Store each user's channel opt-ins, quiet hours, and IANA timezone. Read the record at send time and skip channels the user disabled or that fall inside their quiet window.

// services/preferences.js
import { db } from "../config/aws.js";
import { GetCommand } from "@aws-sdk/lib-dynamodb";
​
export async function getPreferences(userId) {
  const res = await db.send(
    new GetCommand({ TableName: "UserPreferences", Key: { userId } })
  );
  return res.Item ?? { email: true, push: true, sms: false, quietStart: "22:00", quietEnd: "07:00", tz: "America/Los_Angeles" };
}

Wiring email delivery with Amazon SES

Use the SES v2 SendEmail call with a template. Handle bounces and complaints through SNS feedback topics so your reputation stays clean.

// services/email.js
import { ses } from "../config/aws.js";
import { SendEmailCommand } from "@aws-sdk/client-ses";
​
export async function sendEmail(to, templateName, data) {
  await ses.send(
    new SendEmailCommand({
      Destination: { ToAddresses: [to] },
      Template: templateName,
      TemplateData: JSON.stringify(data),
    })
  );
}

The SES developer guide covers template creation and the bounce/complaint flow.

Wiring mobile push and SMS with Amazon SNS

Publish to the SNS topic that maps to each platform. SNS applies its own retry policy (immediate retries, then exponential backoff, then a long fixed-interval tail) so you don't have to build that yourself.

// services/push.js
import { sns } from "../config/aws.js";
import { PublishCommand } from "@aws-sdk/client-sns";
​
export async function sendPush(arn, payload) {
  await sns.send(
    new PublishCommand({ TargetArn: arn, Message: JSON.stringify(payload) })
  );
}

For SMS, use the same PublishCommand with a PhoneNumber instead of a topic ARN. Remember that SMS origination numbers and country registrations live in AWS End User Messaging SMS.

Adding in-app feed and web push (optional)

The router you already have can call an in-app write API and a VAPID web-push endpoint. SuprSend's in-app inbox and the MDN Push API both expose simple HTTP interfaces that fit the same sendViaChannel signature.

// services/inApp.js
export async function writeInApp(userId, eventType, payload) {
  await fetch(`${process.env.INAPP_API}/users/${userId}/notifications`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ eventType, payload }),
  });
}

Testing the end-to-end flow

Trigger each event type with a real user ID and verify:

  1. The router picks the channels the user opted into.
  2. Quiet hours suppress the send until the window opens.
  3. SES returns a MessageId and SNS returns a MessageId for push/SMS.
  4. Delivery logs show "delivered" for email and push; SMS shows "sent" (carrier receipts are async).

Gotchas and operational tips

  • Idempotency: Generate a UUID per logical notification and store it in a deduplication table before you call any provider. The idempotent-consumer pattern prevents double sends when your caller retries.
  • SES sending limits: New accounts start in sandbox mode. Request a production limit increase before you launch here.
  • SNS throttling: Publish calls return ThrottlingException under burst load. Back off with jitter and retry.
  • Preference cache invalidation: If you cache the preference record, invalidate it on every profile update or use a short TTL (30 s).
  • Observability: Emit a structured log line per channel with userId, eventType, channel, providerMessageId, and latencyMs. Ship those logs to CloudWatch or your central store.

Wrapping up

You now have a Node.js service that:

  • Routes events to channels based on stored preferences
  • Sends transactional email through SES with bounce handling
  • Publishes push and SMS through SNS with built-in retries
  • Exposes a slot for in-app and web push without changing the router
