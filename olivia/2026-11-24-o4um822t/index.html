Build a Provider-Agnostic SMS Notification System with Triggers, Retries and Fallback

A provider-agnostic SMS notification system lets you send alerts through any SMS vendor while keeping your application code unchanged. When one provider degrades, the system retries with backoff and fails over to a backup vendor automatically. Get it right and your on-call pages arrive even during a Twilio outage; get it wrong and you silently drop messages or bill for retries that never reach users.

Prerequisites

  • Node.js 20+ and npm for the example code
  • A Twilio account with a verified sender ID and Messaging Service SID
  • An Amazon SNS topic configured for SMS with a spend limit set
  • A workflow engine that supports versioned runs, retries and branching, the examples use SuprSend workflows but the pattern applies to any engine with similar primitives

Setting Up the Project

Initialize a fresh repository and install the vendor SDKs you'll call from the workflow steps.

mkdir sms-alerts && cd sms-alerts
npm init -y
npm install @twilio/sdk @aws-sdk/client-sns

Create a .env file with the credentials each provider needs. Keep the keys out of source control.

TWILIO_ACCOUNT_SID=ACxxxx
TWILIO_AUTH_TOKEN=your_token
TWILIO_MESSAGING_SERVICE_SID=MGxxxx
AWS_REGION=us-east-1
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=...
SNS_TOPIC_ARN=arn:aws:sns:us-east-1:123456789012:sms-alerts

Defining the Trigger Event

Every alert starts as a normalized event so the workflow doesn't care which service originated it. Define a small JSON schema and validate incoming payloads against it.

{
 "$schema": "http://json-schema.org/draft-07/schema#",
 "type": "object",
 "required": ["alertId", "to", "body", "priority"],
 "properties": {
 "alertId": { "type": "string", "format": "uuid" },
 "to": { "type": "string", "pattern": "^\\+[1-9]\\d{1,14}$" },
 "body": { "type": "string", "maxLength": 1600 },
 "priority": { "type": "string", "enum": ["high", "normal", "low"] }
 }
}

Your API endpoint (or a webhook from Datadog, PagerDuty, etc.) posts to this schema. The workflow engine receives the validated payload and starts a run keyed by alertId so duplicate webhooks don't create duplicate messages.

Building the Retry Logic with Exponential Backoff

Transient failures (network blips, 429 responses) should retry; permanent failures (invalid number, blocked sender) should not. Implement a retry helper that wraps any provider call.

async function withRetry<T>(
 fn: () => Promise<T>,
 options: { maxAttempts: number; baseDelayMs: number; isRetryable: (err: unknown) => boolean } = {
 maxAttempts: 3,
 baseDelayMs: 500,
 isRetryable: (err) => err instanceof Error && /^(ECONNRESET|ETIMEDOUT|429|5\d{2})$/.test(err.message)
 }
): Promise<T> {
 let attempt = 0;
 while (true) {
 try {
 return await fn();
 } catch (err) {
 attempt++;
 if (attempt >= options.maxAttempts ||!options.isRetryable(err)) throw err;
 const delay = options.baseDelayMs * 2 ** (attempt - 1) + Math.random() * 100;
 await new Promise((r) => setTimeout(r, delay));
 }
 }
}

The helper uses exponential backoff with jitter so a fleet of workers doesn't hammer a recovering provider all at once. Only errors that match the retryable pattern (connection resets, timeouts, 429, 5xx) trigger a retry. Invalid-number errors (Twilio 21211, 21614) fail fast.

Adding Provider Fallback Routing

When the primary provider returns a permanent failure, route the same alert to a secondary provider. The workflow step looks like this:

async function sendWithFallback(payload: AlertPayload) {
 try {
 return await withRetry(() => sendViaTwilio(payload));
 } catch (primaryErr) {
 if (isPermanent(primaryErr)) {
 console.warn('Twilio permanent failure, falling back to SNS', { alertId: payload.alertId, error: primaryErr });
 return await withRetry(() => sendViaSns(payload));
 }
 throw primaryErr;
 }
}
​
function isPermanent(err: unknown) {
 if (!(err instanceof Error)) return false;
 return /^(21211|21614|21610)$/.test(err.message);
}

Twilio's error dictionary lists codes that indicate a permanent problem such as invalid destination (21211, 21614, 21610). Amazon SNS accepts PhoneNumber and Message parameters via its Publish API, so the payload maps directly Publish API. Set an SNS MonthlySpendLimit to cap costs if the fallback fires heavily.

Wiring It Together in a Workflow Engine

A workflow engine turns the ad-hoc functions above into a durable, observable run. In SuprSend you'd model it as a visual workflow:

  1. Trigger, event ingest (API or webhook) validated against the schema.
  2. Branch, if priority === "high" skip the digest node and go straight to send.
  3. Send primary, function node calling sendViaTwilio with the retry wrapper.
  4. Branch on error, catch permanent failures, log the reason, then invoke the fallback node.
  5. Send fallback, function node calling sendViaSns with its own retry wrapper.
  6. Log result, write delivery status, provider used, latency and error code to the message log.

Figure 1: Trigger → retry → fallback flow inside the workflow engine.

The engine handles idempotency keys (the alertId), versioning (draft/live), and observability (step logs, blocked-send reasons) without extra code. You can also add a throttle node before the send steps to respect per-provider rate limits.

Testing Failure Scenarios

Verify the retry and fallback paths before you ship.

Transient network error. Point the Twilio SDK at a mock server that returns 503 twice then 200. The message should send on the third attempt with latency logged.

Rate limit (429). Mock returns 429 with Retry-After: 1. Backoff should respect the header and succeed on retry.

Invalid destination number. Send to +15550000000 (Twilio test code for invalid). Primary should fail fast with error 21211, and fallback should send via SNS.

Primary provider outage. Block egress to api.twilio.com in CI. All alerts should route to SNS with no alerts lost.

Fallback also fails. Block both egress paths. The run should be marked failed, and the alert should appear in a dead-letter queue for manual review.

Twilio now bills for failed messages that aren't caused by their internal errors, so the test suite should also assert that permanent failures don't generate billable retries.

Wrapping Up

  • Normalize the trigger payload once; every downstream step stays provider-agnostic.
  • Wrap each provider call in a retry helper that distinguishes transient from permanent errors using the provider's own error codes.
  • Fail over to a secondary provider only on permanent failures; keep the same payload shape so the fallback is a drop-in replacement.
  • Run the whole sequence inside a workflow engine so you get durability, observability and versioning for free.
  • Extend next: add a digest node for low-priority alerts, a preference check so users can opt out of SMS, and a webhook callback that updates your own dashboard with delivery receipts.
