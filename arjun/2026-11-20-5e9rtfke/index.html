Using expo-notifications in production: permissions, tokens and receipts

Expo-notifications gives React Native teams a single library for local scheduling and remote push across iOS and Android. Get it right, and you ship a reliable notification experience with one codebase. Get it wrong, and users never see the alerts you depend on for retention.

This walkthrough covers the production details the docs scatter across multiple pages: permission flows that differ by OS version, the two token types you need to manage, and receipt checking that tells you whether a push actually reached APNs or FCM.

Prerequisites

Before you write any notification code, you need:

  • An EAS project, getExpoPushTokenAsync() requires the projectId that EAS provides, and EAS Build manages your push credentials automatically.
  • Apple Developer Program membership ($99/year), required to create APNs keys and provisioning profiles.
  • A Firebase project, FCM handles Android delivery and can relay to APNs if you choose the native route instead of Expo's managed service.

You can test local notifications in Expo Go, but remote push requires a development build from SDK 53 onward. The MDN Push API and MDN Service Worker API define the web standards that Expo's web push implementation follows.

Setting up the project

Install the library and its peer dependencies:

npx expo install expo-notifications expo-constants

Add the config plugin to app.json so native code is generated during prebuild:

{
 "expo": {
 "plugins": ["expo-notifications"]
 }
}

Run a development build for each platform:

npx expo run:ios
npx expo run:android

Requesting notification permissions

Permission handling is where most production apps diverge from the tutorial happy path. iOS and Android 13+ both require explicit user consent, but the APIs and timing differ.

iOS: one system prompt, then Settings

On iOS, getPermissionsAsync() returns the current status. If it's not granted, call requestPermissionsAsync() once. The system shows the prompt a single time; if the user denies, only the Settings app can change it.

import * as Notifications from 'expo-notifications';
import { Platform } from 'react-native';

async function registerForPushNotificationsAsync() {
 if (Platform.OS === 'android') {
 await Notifications.setNotificationChannelAsync('default', {
 name: 'Default',
 importance: Notifications.AndroidImportance.MAX,
 vibrationPattern: [0, 250, 250, 250],
 lightColor: '#FF231F7C',
 });
 }

 const { status: existingStatus } = await Notifications.getPermissionsAsync();
 let finalStatus = existingStatus;
 if (existingStatus!== 'granted') {
 const { status } = await Notifications.requestPermissionsAsync();
 finalStatus = status;
 }
 if (finalStatus!== 'granted') {
 throw new Error('Permission not granted');
 }
}

Android 13+: channel first, then prompt

Android 13 (API 33) requires a notification channel before the permission dialog appears. Create the channel, then request permission. Older Android versions grant notification permission by default.

The code above handles both: the Platform.OS === 'android' block creates the channel, then the permission request follows the same flow as iOS.

Managing Expo push tokens vs native FCM/APNs tokens

Expo's managed push service sits between your backend and the platform gateways. It issues an ExpoPushToken that identifies the device to Expo's servers. Separately, the device holds native tokens (FCM registration token on Android, APNs device token on iOS) that identify it directly to Google and Apple.

Figure 1: Token registration and send flow using Expo's managed service.

Getting the Expo push token

const token = await Notifications.getExpoPushTokenAsync({
 projectId: Constants.expoConfig?.extra?.eas?.projectId,
});
await saveTokenToBackend(token.data); // your API

The projectId comes from your EAS project configuration. Store this token on your backend alongside the user ID. The Apple User Notifications framework and Firebase Cloud Messaging docs describe the native token formats you'll also collect.

Getting native tokens (optional but recommended)

If you want the option to bypass Expo's service later (for example, to use FCM's topic messaging or APNs's Live Activities) capture native tokens in parallel:

// Android (requires @react-native-firebase/messaging in a bare workflow)
import messaging from '@react-native-firebase/messaging';
const fcmToken = await messaging().getToken();

// iOS (Expo handles APNs registration automatically in managed workflow)
// For bare workflow, use expo-device and expo-push-token-native

Store both token types. When the OS rotates tokens (reinstall, backup restore, OS update), the Notifications.addNotificationReceivedListener and messaging().onTokenRefresh callbacks fire, use them to update your backend.

Sending a test notification and checking receipts

Expo's Push API accepts a simple JSON payload. A minimal send from your backend:

curl -X POST https://exp.host/--/api/v2/push/send \
 -H "Content-Type: application/json" \
 -d '{
 "to": "ExponentPushToken[xxxxxxxxxxxxxxxxxxxxxx]",
 "title": "Deployment complete",
 "body": "Your build passed. Tap to view logs.",
 "data": { "screen": "builds", "buildId": "123" }
 }'

The response includes a receipt ID. Poll the receipt endpoint to learn whether Expo successfully handed the notification to APNs and FCM:

curl -X POST https://exp.host/--/api/v2/push/getReceipts \
 -H "Content-Type: application/json" \
 -d '{"ids": ["receipt-id-from-send-response"]}'

Handling foreground, background and tapped notifications

Set a global notification handler to control presentation when the app is in the foreground, and add listeners for user interaction:

import * as Notifications from 'expo-notifications';
import { useNavigation } from '@react-navigation/native';

Notifications.setNotificationHandler({
 handleNotification: async () => ({
 shouldShowAlert: true,
 shouldPlaySound: true,
 shouldSetBadge: false,
 }),
});

function useNotificationListeners() {
 const navigation = useNavigation();

 useEffect(() => {
 // Foreground: show in-app banner
 const foregroundSub = Notifications.addNotificationReceivedListener(
 (notification) => {
 showInAppBanner(notification.request.content);
 }
 );

 // User tapped a notification (any app state)
 const responseSub = Notifications.addNotificationResponseReceivedListener(
 (response) => {
 const { screen, buildId } = response.notification.request.content.data;
 if (screen === 'builds') {
 navigation.navigate('BuildDetail', { buildId });
 }
 }
 );

 return () => {
 foregroundSub.remove();
 responseSub.remove();
 };
 }, [navigation]);
}

The data payload you sent travels with the notification and survives app restarts.

Gotchas: token rotation, rate limits and Expo Go limitations

Token rotation happens on app reinstall, device restore, and OS major upgrades. Both Expo and native tokens rotate. Listen for changes:

// Expo token
Notifications.addNotificationReceivedListener(() => {
 Notifications.getExpoPushTokenAsync().then(saveTokenToBackend);
});

// Native FCM token (bare workflow)
messaging().onTokenRefresh((token) => saveFcmTokenToBackend(token));

Rate limits: Expo caps sends at 600 notifications per second per project.

Expo Go limitation: From SDK 53, Expo Go does not support remote push notifications. You must use a development build or a standalone app binary to test push.

Wrapping up

  • Two token strategies: ExpoPushToken for the managed service (simplest, good for most product notifications), native FCM/APNs tokens for full control (topics, Live Activities, direct provider contracts).
  • Receipts are mandatory: poll them after every send batch to purge invalid tokens and catch gateway errors early.
  • Permission flows diverge: iOS is one prompt forever; Android 13+ needs a channel first, then a runtime prompt. Handle both or users silently opt out.
  • Migrate to native when: you need FCM topics, APNs Live Activities, or want to negotiate your own provider contracts. The native tokens you already collect make that switch a backend change, not a client rewrite.

For the complete API reference, see the Expo notifications documentation and Firebase Cloud Messaging docs.
