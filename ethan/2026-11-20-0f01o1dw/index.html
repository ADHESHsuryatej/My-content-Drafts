Vendor fallback in SuprSend: what happens when your email provider goes down mid-send

email provider failover notifications keep transactional messages moving when your primary vendor returns a retryable error.

A password reset, an OTP, or a receipt is triggered by a user action right now. If your email vendor is down, the message sits in your queue or fails silently. Most teams don't build a second provider integration until the first one burns them. SuprSend's smart routing treats providers as interchangeable nodes: you configure a primary and a backup per category (system, transactional, promotional), and the platform switches automatically when the primary returns a retryable error.

The problem: provider outages hit transactional email hardest

Transactional email has no patience. A password reset that arrives in five minutes is a support ticket. An OTP that never arrives is a lost user. When SendGrid or Amazon SES returns a 5xx error, your application code usually has no plan B. SuprSend's orchestration layer sits between your trigger and the provider, so a single vendor outage doesn't stop transactional email.

How SuprSend handles vendor fallback

The flow is a short sequence: your app calls the workflow API → SuprSend picks the primary vendor for that notification's category → the vendor accepts or rejects → on a retryable error (network timeout, 5xx, rate limit) SuprSend re-queues the same rendered payload to the backup vendor → a webhook fires with the fallback event so your observability stack knows what happened.

Figure 1: Provider failure triggers fallback send and a webhook event.

Per-category routing means your marketing emails can fail over to a different backup than your password resets. You set the order in the dashboard or via the Management API. The same payload renders once; only the transport changes. If both vendors fail, the message is marked blocked and the reason appears in the message logs.

What using it actually involves

  1. Add vendors in Settings → Channels → Email. Connect SendGrid, Amazon SES, Resend, Postmark, Mailgun, Mailjet, or an SMTP endpoint. Each connection stores credentials and a verified sending domain.
  2. Set primary and backup per category (system, transactional, promotional) in the smart routing UI. Drag to reorder; the top vendor is tried first.
  3. Test in the sandbox workspace using SuprSend's test vendors. They simulate success, 4xx, and 5xx responses so you can verify the fallback path without sending real email.
  4. Watch the webhooks: SuprSend emits webhook events for delivery status changes; exact event names and payloads are documented in the webhook docs.

Caveats

  • Plan gating for vendor fallback is not documented in the fact sheet. Verify current limits on SuprSend's pricing page.
  • No retry on 4xx errors (invalid recipient, rejected template, suspended account). Those are treated as deterministic failures; the message is blocked immediately and the webhook reports the provider's exact response.
  • Log retention varies by plan: 30 days on Free, 90 days on Essentials and Business, custom on Enterprise. If you need a longer audit trail for compliance, factor that into the plan choice.
  • Self-hosted and BYOC deployments mirror the same routing logic, but you operate the Kubernetes cluster or the cloud account. The fallback behavior is identical.
