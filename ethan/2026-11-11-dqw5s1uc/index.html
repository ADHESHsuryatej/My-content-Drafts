How Push Notifications Work

Push notifications are messages delivered to a user's device even when your app isn't open. Get the path right, and a critical alert reaches the user in seconds. Get it wrong, and your logs show "accepted" while the phone stays silent.

The Stakes of Delivery

Your server receives a 200 OK from APNs or FCM. That response only means the gateway accepted the request. The message can still be dropped because the device token rotated, the payload exceeded the limit, or the user disabled notifications for your app. You won't see those drops in the gateway response.

The Journey in Four Steps

Here's how it works: the user installs the app, the device asks APNs or FCM for a token, your server stores that token, and later your server sends a payload to the gateway with the token as the address. The gateway routes the message to the specific device. The OS wakes your app (or shows the alert directly) and your code handles the payload.

Figure 1: How a push notification travels from your server through APNs or FCM to the user's phone.

On iOS the device token can change after an OS update or a reinstall. On Android the FCM registration token rotates periodically. If your server keeps an old token, the gateway returns a 410 or invalid_token error, but only if you check the response. Many integrations log the 200 and move on.

Where It Breaks

Token rotation is the most common silent failure. Payload limits are the next: APNs caps at 4 KB, FCM at 4 KB for both data and notification messages (HTTP v1 API). Larger payloads are rejected. Collapse identifiers on iOS and collapse_key on Android let newer messages replace older ones, but if the device is offline the gateway keeps only the latest. The user sees one alert instead of five. Nielsen Norman Group notes that users often disable channels that feel noisy, so a collapsed burst can look like a single ignored notification.

The hardest problems aren't solved when you finish building your push notification infrastructure. Building one doesn't matter unless you have the specifics of your customer behaviour straight. These patterns make it easier for push notifications to succeed.

Recap

  • The gateway 200 is not delivery; instrument token invalidation callbacks and FCM sent/delivered receipts.
  • Track token rotation rates, payload size errors, and collapse-key drops per campaign.

RFC 8030 defines the web push protocol if you need the same flow for browsers.
