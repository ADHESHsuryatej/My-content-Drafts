How to set up Android push notifications with Firebase Cloud Messaging

Push notifications are messages delivered to a user's device even when your app isn't open. Get them right and users see timely updates; get them wrong and you waste battery, miss messages, or drive uninstalls.

Prerequisites

Before you write code, gather these pieces:

  • Android Studio (Giraffe or later) with an Android 7.0+ emulator or device that has Google Play Services.
  • A Firebase project. Create one in the Firebase console if you don't have one.
  • The google-services.json file downloaded from that project and placed in your app module's app/ directory.
  • A backend server (or Cloud Function) that can call the FCM HTTP v1 API with a service account. Firebase Cloud Messaging Android setup

Requesting the registration token on the client

In your main activity's onCreate, request the current token and send it to your server with a timestamp. The token can rotate, so onNewToken will fire again when it does.

On your server, store the token alongside the user ID and a last_updated timestamp. Schedule a monthly job to refresh tokens by calling the same client method or by relying on onNewToken. Firebase considers a registration expired after 270 days of inactivity and will reject sends to it. Manage FCM registration tokens

Handling background and terminated states

FCM treats messages differently based on app state and message type:

Foreground. Both notification and data messages arrive in onMessageReceived.

Background. Notification messages appear in the system tray; data messages still call onMessageReceived.

Terminated. Notification messages appear in the system tray; data messages call onMessageReceived via WorkManager.

When your app is in the background, a notification message appears in the system tray. A tap opens the launcher activity with the data payload in the intent extras. For data-only messages in the background, onMessageReceived still fires but you have a short execution window (a couple of seconds). Offload long work (network calls, image downloads) to WorkManager.

Notification messages are always collapsible; data messages are not. Receive messages on Android

Gotchas: token expiration, payload limits and permission on Android 13+

  • Token expiration: FCM garbage-collects registrations inactive for 270 days. Your monthly refresh job prevents stale tokens from polluting your send list. Manage FCM registration tokens
  • Payload limit: Both notification and data messages cap at 4096 bytes (the Firebase console enforces a 1000-character limit). Keep custom keys short.
  • Android 13+ runtime permission: Apps targeting API 33+ must request POST_NOTIFICATIONS at runtime before any notification can appear. Call ActivityCompat.requestPermissions in your first activity and handle the callback. Android notification permission

Wrapping up

  • Token flow: Client requests token → sends to your server → server stores with timestamp → monthly refresh keeps it fresh.
  • Server send path: Your server calls FCM HTTP v1 API (via Admin SDK or REST) with the stored token and either notification or data payload.
  • Two message types: Notification messages for automatic display; data messages when your app needs full control.
  • Monitor: Open the Firebase console → Messaging → Reports to watch delivery, open and error rates per campaign.

With these pieces wired, you own the full push stack without a third-party wrapper.
