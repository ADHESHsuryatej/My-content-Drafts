Designing a Notification System: Queues, Idempotency, Data Model and Build-vs-Buy

A notification system moves events from your application to the right channel for each user without losing, duplicating or delaying messages. Get it right, and users act on time-sensitive alerts. Get it wrong, and you ship duplicate pushes, miss critical emails or spend weeks debugging queue backlogs.

Figure 1: End-to-end flow from event ingestion to provider delivery.

What a notification system actually does

The system owns six responsibilities: ingestion, queuing, templating, routing, delivery and observability. Ingestion accepts an event payload from your code and validates it against a schema. Queuing buffers the work so traffic spikes don't crash downstream handlers. Templating renders channel-specific content from a single source of truth. Routing decides which channels a user receives based on preferences, tenant defaults and channel health. Delivery calls the provider API (APNs, FCM, SendGrid, Twilio) and handles retries. Observability logs every step so you can trace a notification from trigger to click. Knock's guide to push delivery notes that building all of this yourself means maintaining token management, provider integrations, preference systems and analytics on top of the core delivery logic.

Choosing the queue backbone: RabbitMQ vs Kafka

Notifications are independent units of work: each one must be routed, rendered and acknowledged separately. RabbitMQ models this natively with queues that track per-message delivery state, support TTL, priorities and delayed retries, and replicate acknowledgements through Raft before they take effect. Kafka 4.2 added share groups that let consumers acknowledge individual messages under a lock, but the log remains the source of truth and queue semantics are a consumption mode layered on top. For most notification workloads, RabbitMQ's queue semantics (hold until 14:32, retry one message in three minutes, dead-letter the poison pill) map directly to the operational knobs you need. Use Kafka when you already run it for event streaming and want a single broker; use RabbitMQ when you want a queue that behaves like a queue.

Making consumers idempotent so retries don't duplicate sends

At-least-once delivery means the same message can arrive twice: producer retries, missing acknowledgements, or a crash after the database write but before the ack. The fix is a stable deduplication key that identifies the logical operation, not the transport envelope. Extract a producer-assigned message ID or a business-level idempotency key (for example, user:123:password_reset:2026-11-15). Check a persistent store (Redis SET with TTL, a Postgres unique index, or a dedicated deduplication table) for that key. If it exists, ack and stop. If not, process and record the key in the same transaction. Propagate the key to any downstream service so they can deduplicate their own writes. This pattern turns at-least-once into effectively-once without requiring exactly-once semantics from the broker.

Data model and schema: users, channels, templates and events

Start with four core entities. Users (or recipients) store channel addresses (email, phone, apns_token, fcm_token, web_push_subscription) plus a locale and timezone. Channels define the provider mapping and fallback order per category (transactional, marketing, security). Templates hold channel-specific content (subject, body, Handlebars/JSONNET partials) versioned per locale. Events capture the trigger payload with a JSON Schema so consumers can validate before rendering a few words A minimal notification_event schema includes event_id (UUID), event_type (slug), recipient_id, payload (object), created_at and idempotency_key. Store templates and channel configs in versioned rows so you can roll back a bad edit without a code deploy.

Handling multi-channel routing and user preferences at send time

Routing resolves at send time, not at template author time. A routing service checks: is the channel enabled for this category? Does the user have a valid address for it? What does the user's preference centre say, opted out, digest-only, or specific channels? What is the tenant default? Courier's routing guide describes layering topic defaults, tenant overrides and user choices, with a REQUIRED flag that forces delivery for critical flows like two-factor codes. Build the router as a pure function: input (event, user profile, tenant config) → output (ordered channel list). That makes it testable, observable and replaceable without touching the queue consumer.

Closing recap

  • Architectural checklist: queue with per-message durability (RabbitMQ), stable deduplication keys stored atomically, versioned templates with JSON Schema validation, pure-function router that respects user and tenant preferences, observability on every hop.
  • Build-vs-buy rule: if you're not solving HIPAA, billions-of-messages scale, sub-millisecond latency or white-label multi-tenancy, a managed platform returns months of engineering time to your core product.
