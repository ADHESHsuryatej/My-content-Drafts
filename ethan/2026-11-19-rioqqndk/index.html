Notification message logs: what to capture per send, delivery status, retention and debugging

Message logs are the immutable record of every notification your system attempts to deliver. Get them right, and you can trace a failed password-reset email to a specific provider rejection in seconds. Get them wrong, and you're guessing why users never saw the alert.

The stakes of incomplete logs

When a user says "I didn't get the email," the first question is whether your system even tried to send it. If your logs only store a success flag from the provider's HTTP response, you lose the context that explains a soft bounce, a spam complaint, or a delayed delivery. Amazon SES publishes bounce, complaint, and delivery notifications to Amazon SNS as JSON objects that include the original message metadata and the provider's per-recipient status a few words. Without capturing that full payload, you cannot distinguish a transient deferral from a permanent block, and you cannot prove to a compliance auditor what actually happened.

What a complete message log captures per send

Every log entry should answer who, what, when, where, and how the provider responded. The essential fields are:

  • Message ID, your internal UUID that ties the log row to the business event (order placed, password reset, weekly digest).
  • Recipient identifier, the email address, phone number, device token, or in-app user ID.
  • Channel, email, SMS, push, in-app, Slack, WhatsApp.
  • Payload hash, a SHA-256 of the rendered content so you can verify exactly what was sent without storing PII in the log row.
  • Timestamps, created_at (when your app queued the send), provider_submitted_at (when the HTTP call returned), provider_finalized_at (when the webhook arrived with the terminal status).
  • Provider response, the raw JSON from the provider's webhook, including the DSN action and status fields for email, the message_id from FCM or APNs for push, and the MessageSid from Twilio for SMS a few words.

RFC 3464 defines the action field (failed, delayed, delivered, relayed, expanded) and the status code (e.g., 2.0.0 for success, 5.1.1 for bad destination mailbox) that every standards-compliant MTA returns. Storing those two fields lets you map any provider's response to a unified state machine.

Delivery status lifecycle you can actually trace

Providers use different vocabularies, but the state graph is the same. Map every inbound webhook to one of:

Queued. Your system accepted the request (API 202 response). Submitted. Provider accepted the message (SES delivery webhook, SendGrid processed). Delivered. Remote MTA accepted the message (SES delivery with status 2.x.x). Deferred. Temporary failure, will retry (SES bounce with action delayed, 4.x.x status). Bounced. Permanent failure (SES bounce with action failed, 5.x.x status). Complained. Recipient marked spam (SES complaint webhook). Opened / Clicked. Engagement (provider tracking pixel or link wrapper).

SES notifications include a timestamp (ISO 8601) and processingTimeMillis so you can measure latency from submit to final delivery. Knock applies a plan-based retention policy to message log data: Enterprise plans keep it for 90 days, all other plans for 30 days, while in-app feed notifications remain available indefinitely. Build your own state machine once, then every channel feeds into it.

Retention policies that balance cost and debugging

Hot storage (queryable in your dashboard or via API) should cover the debugging window. Cold storage (object store, Parquet, warehouse) covers compliance and trend analysis.

  • 30 days hot, covers most "user didn't get it" tickets and sprint-cycle debugging.
  • 90 days hot, required if you support Enterprise SLAs or need to correlate a delivery failure with a downstream churn event.
  • 1–7 years cold, GDPR Article 7 and financial regulations often require proof of consent and transactional delivery. Export logs to S3 as Parquet with a partition per day; keep the payload hash but drop the rendered HTML to reduce PII surface.

Knock's universal 30-day retention applies to API logs regardless of plan, while message log data follows the plan tier. Amazon WorkMail lets you set folder-level retention with a "Delete" or "Permanently delete" action and a configurable day count. Choose your hot window based on the longest feedback loop you support (e.g., a weekly digest that users might report missing after two weeks).

Debugging workflows that use your logs

Logs are only useful if you can answer questions fast. Three patterns turn raw rows into signal:

  1. Correlate with user reports, when a support ticket arrives, search by recipient and 48-hour window. The payload hash lets you diff what you sent against what the user shows you (forwarded email, screenshot).
  2. Replay failed sends, a bounced row with a 5.1.1 status means the address is dead; suppress it. A 4.4.1 (connection timed out) means the provider will retry; do not resend manually or you'll duplicate.
  3. Alert on anomaly patterns, graph the ratio of bounced to submitted per provider per hour. A jump triggers a PagerDuty alert. Braze's Message Activity Log caps error logs at 20 per error type per campaign per hour, which hides sustained spikes; your own store should not.

Verbose SDK logging helps on the client side: Braze recommends enabling debug-level logs before reproducing a missing push or in-app message, then sharing the V/Braze Logcat output with support. On the server side, your log store is the source of truth.

Email delivery tools that surface the right data

Not all providers expose the same granularity. What to verify before you commit:

Amazon SES. Publishes the full DSN via SNS: bounce, complaint, and delivery objects with action, status, remoteMtaIp, and processingTimeMillis. You own the SNS topic, so you can fan out to Lambda, Firehose, or your own webhook endpoint. SendGrid. Event Webhook delivers processed, delivered, deferred, bounce, block, spam_report, open, click. The bounce event includes a reason string and SMTP code, but the raw DSN is not guaranteed. Resend. Webhooks include email.sent, email.delivered, email.bounced, email.complained. The bounce payload surfaces the status_code and diagnostic_code from the remote MTA. Postmark. Bounce webhook returns the full RFC 3464 DSN fields: Type, TypeCode, Name, Tag, Message, ServerID, Metadata, and the original headers. This is the closest to a raw DSN you get without running your own MTA.

If your provider doesn't surface remoteMtaIp or the raw Diagnostic-Code, you cannot tell whether a block is at the inbox provider (Gmail, Outlook) or an intermediate gateway. That distinction changes the remediation from "clean your list" to "warm a new IP pool."

Close

  • Capture message ID, recipient, channel, payload hash, triple timestamps, and the full provider webhook payload.
  • Map every provider response to a unified state machine built on RFC 3464 action and status codes.
  • Keep 30–90 days hot for debugging; archive everything else to cold storage with PII minimized.
  • Alert on bounce-rate deltas, not absolute counts.
  • Verify your email provider returns the remote MTA IP and diagnostic code before you sign the contract.

The habit that prevents blind spots: treat the log write path as a first-class API contract. If the webhook handler fails, the send is not "done", it's "unconfirmed," and your alerting should fire.
